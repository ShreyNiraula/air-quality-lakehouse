# Check 0.3: dbt

Run on 6 October 2026 (UTC). The check passes, with a limit that later tasks must know: dbt builds a model into the Iceberg catalog only as an **incremental** model. The catalog refuses a plain table and a view. The script's unedited output is in `generated/0.3-dbt.md`.

## How to run it

```
make dbt-check
```

It starts the object store and the catalog, then runs `uv run python -m airquality.checks.dbt_build`. The script builds the small dbt project in `dbt_check/` several times and prints each result next to what was found with the pinned versions. The last line is `PASS` or `FAIL`.

## What was tested

| Part | Version | Pinned in |
|---|---|---|
| dbt | dbt-core 1.12.5 | `pyproject.toml` |
| dbt's DuckDB adapter | dbt-duckdb 1.11.0 | `pyproject.toml` |
| Query engine | DuckDB 1.5.6 | `pyproject.toml` |
| Store and catalog | as in check 0.2 | `compose.yaml` |

The three versions are now exact pins, not lower bounds. dbt runs DuckDB in memory with the catalog attached; `dbt_check/profiles.yml` shows how.

## What works

- **A seed.** `dbt build` loads a CSV file into an Iceberg table, and loads it again on the next build without doubling the rows.
- **An incremental model that replaces rows by key.** Built twice, it holds 2 rows, not 4, and its table has 3 snapshots.
- **Data tests.** `unique` and `not_null` on the model pass.

## What the catalog refuses

Each of these is a step of the script, with the exact message in the output.

- **A plain table.** dbt first creates the table under a temporary name and then renames it. The catalog cannot rename a table in the transaction that created it.
- **A view.** Creating a view is not implemented.
- **`--full-refresh`.** dbt reports an error, but the change is not undone. The old table is left behind as `readings__dbt_backup` with its 3 snapshots, and a new table with 1 snapshot has taken the model's name. A command that failed has replaced the table readers see, so `--full-refresh` must not be run against the catalog.

## What later tasks need to know

- **The model layers cannot be plain tables or views inside the catalog.** `plan.md` builds raw, hourly, daily and comparison tables with dbt. With these versions each of them is either an incremental model in the catalog, or it is built outside the catalog, in a plain DuckDB database where every kind of model works, and copied in when it is published. `plan.md` already separates the candidate build from the promotion, so both fit it. Which one to use is not decided here; it belongs to the planning of milestone 1.
- **Seeds work**, so task 1.2 can load the vocabulary and the registry into the catalog.
- **Tried by hand, not by the script:**
  - An enforced contract works on an incremental model if `on_schema_change` is set to `fail`, and a model that breaks its contract is refused.
  - Through DuckDB the catalog also refuses `CREATE OR REPLACE TABLE`, and a `DROP TABLE` followed by `CREATE TABLE` of the same name in one transaction. `DELETE` and `TRUNCATE` work.
  - DuckDB leaves an empty folder named `data` in the working directory when it creates an Iceberg table from a query. The script runs dbt from a temporary folder for this reason.
- **Not checked here:** dbt snapshots, which the station history may use, and publishing several tables in one step.
