# Check 0.2: Lakehouse

Run on 6 October 2026 (UTC). The check passes: DuckDB creates an Iceberg table through the REST catalog, inserts into it twice, and reads it as it was after the first insert. The fallback, writing with PyIceberg, is not needed. The script's unedited output is in `generated/0.2-lakehouse.md`.

## How to run it

```
make lakehouse
```

It starts the object store and the catalog with `docker compose up -d --wait`, then runs `uv run python -m airquality.checks.lakehouse`. The last line is `PASS` or `FAIL`. The first run downloads three images, about 420 MB (1.2 GB once unpacked), and two DuckDB extensions.

## What was tested

| Part | Version | Where it comes from |
|---|---|---|
| Object store | RustFS 1.0.1 | `rustfs/rustfs` on Docker Hub |
| Catalog | Iceberg REST fixture 1.10.1 | `apache/iceberg-rest-fixture` on Docker Hub |
| Query engine | DuckDB 1.5.6, with its `iceberg` and `httpfs` extensions | PyPI, pinned in `uv.lock` |
| Bucket creation | curl 8.22.0 | `curlimages/curl` on Docker Hub |

## The object store is RustFS, not MinIO

`plan.md` named MinIO. On 6 October 2026 MinIO could not be started as the plan describes:

- Docker Hub denies access to the image `minio/minio:latest`, and answers "not found" (404) for the repository.
- The GitHub API reports the project `minio/minio` as archived, last changed on 24 April 2026.

RustFS speaks the same S3 protocol, is published under Apache-2.0, and has an official image with version numbers. The owner chose it on 6 October 2026, and `plan.md` and `ROADMAP.md` now say RustFS. A trial by hand with a third-party build of MinIO (`cgr.dev/chainguard/minio`) also passed the same steps, so nothing in the check depends on which S3 store is behind it.

## What later tasks need to know

- **The catalog is a test fixture.** Apache Iceberg's own name for it is "Iceberg REST Catalog Adapter Test Fixture". It has no login. That is enough for a lakehouse on one machine; it is not something to put on a network. `compose.yaml` publishes both ports on `127.0.0.1` only, so other machines cannot reach the catalog or the store.
- **The catalog remembers its tables only because of one setting.** `CATALOG_URI` in `compose.yaml` puts its list of tables in a file on a volume. Without it the list is kept in memory. Checked by hand: a table was still readable after `docker compose down` and `docker compose up -d --wait`.
- **Dropping a table leaves its files in the store.** Checked by hand: after `DROP TABLE`, five files of the table were still in the bucket. A table created again under the same name shares that folder. The check uses a new table name on every run for this reason.
- **The store's key and password are in `compose.yaml` in plain text.** They belong to this local store only and protect nothing.
- **Not checked here:** updates and deletes, schema changes, and writing from dbt. dbt is task 0.3; the others are the lakehouse demos of milestone 5.
